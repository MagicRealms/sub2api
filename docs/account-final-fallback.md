# 账号最终保底

账号可以同时绑定正常分组和保底分组。保底支持 OAuth、API Key 等现有账号类型，不自动改变账号类型或上游平台。

账号列表的分组列与展开列表会在保底归属旁显示「保底」标记；展开列表分别列出正常与保底分组。分组管理的账号统计显示正常与保底账号数量，保底数量包含在总量中。这是账号与该分组的关系，不代表整个分组被设为保底。

执行顺序为：已选分组的普通账号按原规则重试、换号及分组回退 → 各已选分组的保底账号 → 仍失败则返回错误。开启后，账号在保底分组中不参加普通调度；在正常分组中继续正常调度。一个分组可以有多个保底账号，保底池内仍沿用已有优先级和负载规则。

配置存储在账号 extra 的 `account_final_fallback_enabled` 和 `account_final_fallback_group_ids` 中。正常与保底分组的并集存入既有账号分组关系，以复用授权边界、模型目录、快照失效与调度检查；不新增跨组越权入口，不需要数据库迁移。

仅对现有允许重放的 HTTP POST 推理接口启用最终阶段，包括 Responses、Chat Completions、Messages、Gemini generateContent 及现有可重试图像接口。模型发现、监控探针和已经建立的 WebSocket 会话不触发额外重放。HTTP `previous_response_id` 续接、工具结果和其他绑定上游状态的请求继续遵守已有兼容性限制。

最后一个正常阶段必须允许重试且没有已计费、正文或工具输出，才允许进入保底。权限、客户余额/额度、请求参数、内容策略拒绝、请求取消及内部定价/策略读取故障不触发。账号冷却或全部不可用可以触发。单次请求最多尝试三个不同保底账号；同一账号不会跨分组重复尝试，账号内部重试仍受现有次数及请求截止时间约束。

保底复用完整认证与分组中间件，继续按原组校验模型白名单、接口能力、上游平台、隐私、账号额度与健康、并发、利润门、客户限制和计费。已有多组计费下限继续生效。使用记录保留原分组与实际账号，运行日志记录最终保底触发。

关闭开关时须显式保存新的正常分组；关闭不会将原保底分组自动提升为正常分组。修改正常分组时保留已配置保底关系，须在账号编辑器单独调整保底配置。
